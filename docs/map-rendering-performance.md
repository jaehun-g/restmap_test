# 지도 조회·마커 렌더링 성능 개선

작업일: 2026-10-22 (한국시간)

## 변경 내용

### 최초 조회 경량화

- `/api/rest-areas`에서 음식 메뉴 전체 JSON 집계를 제거했다. 현재 요약 지도에서 사용하지 않는 `foodMenuSummary`를 만들기 위해 메뉴 테이블을 읽지 않는다.
- 음식 탭은 기존 `/api/rest-areas/{id}/food-menus`를 통해 필요한 휴게소의 메뉴만 조회한다.
- 최초 주유소 요청의 고정 150ms 대기를 제거했다. 이후 연속 검색 범위 변경에는 기존 150ms 지연을 적용한다.
- 휴게소를 다시 조회할 때 기존 데이터를 즉시 지우지 않아, 조회 중 기존 마커가 불필요하게 사라지지 않는다.

### 조회 결과 캐시

- Next.js의 `use cache`, `cacheLife`, `cacheTag`를 사용한다. 새 의존성은 추가하지 않았다.
- 서버 캐시는 60초 후 재검증 대상이 되며, 120초가 지나면 새 데이터를 기다린다. 기본 메모리 캐시이므로 인스턴스 재시작·콜드 스타트 시 다시 조회할 수 있다.
- 휴게소는 공통 스냅샷을 캐시한다. 주유소는 EX/전체 원본별 공통 스냅샷을 캐시한 후 요청받은 반경·지도 경계를 적용한다. 사용자별 좌표를 서버 캐시 키로 저장하지 않는다.
- 노선 주유소 조회는 노선별 결과를 캐시하며, 기존 노선 근접 거리 조건을 유지한다.
- 관리자 조회와 `x-map-fresh: 1` 요청은 서버 캐시를 우회한다. 명시적인 다시 조회와 오류 후 재시도에도 이 헤더를 사용한다.
- 관리자 저장·EX 동기화·유가 Cron·음식 Cron이 성공하면 관련 태그를 즉시 만료시킨다. DB를 직접 수정하는 외부 CLI 작업은 이 태그를 만료시키지 않으므로 최신 조회 또는 시간 기반 만료로 확인해야 한다.
- 브라우저 주유소 검색 캐시는 각 탐색 화면의 메모리에만 보관한다. TTL 30초, 최대 20개 검색 범위로 제한하고 원본·노선·좌표·반경이 다른 검색은 분리한다. 수동 새로고침과 저장 시 이전 범위의 캐시도 지운다.
- HTTP 응답은 `no-store`를 유지하고, 조회 성능은 위 서버 캐시와 명시적인 브라우저 메모리 캐시로 개선한다.
- API의 `Server-Timing: map-query;dur=...` 헤더에서 서버 조회 구간의 소요 시간을 확인할 수 있다.

### 마커 변경분 갱신

- 지도 레이어가 `update()`를 제공하며, 검색 결과가 변해도 기존 레이어·클러스터러·유지되는 마커 객체를 재사용한다.
- 추가·제외·좌표·아이콘·그룹 구성 등 표시 단위가 달라진 항목만 생성·제거한다. 클러스터 변경분을 일괄 반영한 후 한 번 다시 그린다.
- 음식·유가 등 상세 데이터 변경은 마커 생성 기준에서 분리했다. 클릭 시 최신 레코드를 사용하고 선택된 카드도 최신 데이터로 갱신한다.
- 최초 데이터가 비어 있다가 EX 주유소가 추가되어도 올바른 아이콘을 사용하도록 이미지 생성을 지연하고 재사용한다.
- 휴게소·주유소 연결은 원본 데이터가 바뀔 때만 계산한다. 검색·필터와 상세 연결 목록은 이를 공유한다. 연결 목록 조회는 휴게소별 반복 전체 검색 대신 Map 인덱스를 사용한다.

- 관련 단위 테스트 36개 통과: 캐시 만료·범위 격리·용량 제한·초기화, 마커 재사용·추가·제외·최신 데이터, 시설 연결·필터, Cron 인증·오류 처리.
- SDK 모의 브라우저 시나리오 6개 통과: 모바일/PC 양방향 유가·주유소 이동, 줌 재조회, 검색 시 마커 재사용, 동일 반경 복귀 시 요청 재사용 및 재시도, 지도 응답과 독립적인 음식 메뉴 조회.
- 실제 Kakao SDK 시나리오 10개 통과: 모바일/PC의 실패 후 재시도, 목록 선택·줌·화면 크기 변경, 선택 해제, 클러스터 목록·검색·방향 필터, 동일 좌표 그룹.
- 실제 SDK 테스트의 과거 5개 통합 마커 기대값을 현재 정책인 휴게소 4개·주유소 2개의 정확한 이름 목록 비교로 수정했다. 지도 표시 정책은 이번 작업에서 바꾸지 않았다.
- 실제 DB를 읽는 로컬 프로덕션 API 검증 1개 통과: 캐시 응답의 수집 시각 재사용, 최신 조회 우회, 음식 요약 제거, 서로 다른 위치 반경·지도 경계의 결과가 DB 직접 조회와 일치함을 확인했다. 이 테스트는 DB를 수정하지 않는다.
- 변경 파일 ESLint, TypeScript, 프로덕션 빌드 통과.

## 초기 표시·중복 조회 추가 개선 (2026-10-26)

- 최초에는 휴게소·주유소 조회가 모두 끝난 뒤 두 종류의 마커를 함께 표시한다. 어느 응답이 먼저 도착하더라도 일부 마커만 먼저 표시하지 않는다. 이후 조회에서는 기존 마커 유지와 줌인 즉시 반영 정책을 유지한다.
- 모바일의 일반 검색은 `/api/gas-stations?source=ex`로 전국 EX 목록을 한 번 받고, 현재 위치 반경·줌·지도 내 재검색은 기존 브라우저 필터를 적용한다. 위치 확인 때문에 진행 중인 전국 요청을 취소하거나 범위별로 재요청하지 않는다.
- 노선 선택은 기존 서버의 노선 근접 검색을 유지한다. 전체 노선으로 돌아오면 기존 30초 메모리 캐시에 남은 전국 응답을 재사용한다. 관리자 화면의 범위별 최신 조회 방식은 유지한다.
- 표시할 휴게소 배열을 메모이제이션하여 패널·화면 크기 등 데이터와 무관한 상태 변경에서 지도 데이터 갱신을 줄인다.
- 전국 목록 자체의 전송량과 최초 마커 객체 수는 줄이지 않는다. 줌·지도 내 재검색만으로 유가를 다시 수집하지 않으며, 화면 재진입이나 명시적인 다시 조회는 기존 API 캐시·최신 조회 정책을 따른다. 새 의존성은 추가하지 않았다.

검증:

- 관련 단위 테스트 53개 통과: 시설 연결·필터, 공간 검색, 주유소 쿼리, 마커 재사용, 지도 범위 정책.
- SDK 모의 브라우저 테스트 9개 통과: 휴게소·주유소 각각의 응답을 지연해도 두 종류 마커를 함께 표시하고 위치 확인 후 동일 요청 유지, 확대·축소 및 지도 내 재검색에서 요청 1회 유지와 범위별 목록·마커 갱신, 노선 서버 검색과 전국 목록 캐시 복귀, 조회 실패 후 최신 조회 재시도, 기존 상세·음식 조회.
- 변경 파일 ESLint, TypeScript 검사와 프로덕션 빌드 통과. 첫 빌드는 Next.js 보안 업데이트 알림으로 종료되었고, 같은 명령 재실행으로 빌드가 완료됐다. 의존성 버전은 변경하지 않았다.
- 이번 검증은 조회 순서·요청 횟수·화면 동작에 대한 검증이다. 실제 DB·Kakao SDK를 사용하는 운영환경의 시간 단축량은 별도로 측정해야 한다.

## 서버 초기 조회·SDK 조기 로딩 (2026-10-26 추가)

### 최종 동작

- `/mobile`에서 런타임 요청이 시작되면 기존 서버 캐시를 통해 휴게소·전국 EX 주유소 조회를 함께 시작한다. DB 연결 풀과 기존 캐시 수명은 변경하지 않았다.
- 초기 화면은 조회 완료와 독립적으로 렌더링한다. 서버 결과는 Promise로 스트리밍하고, 클라이언트 훅이 이를 받아 최초 API 요청 두 개를 생략한다. 휴게소·주유소 마커는 두 결과가 모두 준비된 후 함께 표시한다.
- SDK URL을 공통 함수로 관리하고 초기 HTML에서 preload한다. 작은 클라이언트 컴포넌트가 기존 단일 SDK 로더를 호출해 데이터 조회 중 SDK 초기화도 진행한다. 지도 컴포넌트는 같은 로딩 Promise를 재사용한다.
- 서버 조회가 실패하면 기존 오류 화면과 명시적인 최신 조회 재시도를 유지한다. 초기 데이터의 스트리밍 전달 자체가 실패하면 기존 API 경로로 복구한다. 관리자는 기존 최신 API 조회를 유지한다.
- 시설 연결 시 노선별 후보 인덱스를 만들고 이름·방향 정규화를 레코드별로 한 번 수행한다. 거리 300m, 방향 우선순위, 검증된 원천 코드 예외, 거리 동률 시 원본 순서 정책은 유지한다.
- 새 라이브러리는 추가하지 않았다. 상세 화면의 추가 코드 분할은 이번 단계에서 적용하지 않았다.

### 실제 데이터·SDK 측정

로컬 프로덕션 빌드, PC Chromium의 390×844 화면, 위치 권한 허용(37.5, 127), 네트워크·CPU 제한 없음. 루트 URL 접속과 리다이렉트를 포함하며, 로드된 마커 이미지가 화면 안에 표시되는 것을 확인한 다음 프레임을 표시 시점의 근사값으로 기록했다. 각 실행에서 새 브라우저 컨텍스트 3개를 만들고 각 컨텍스트에서 최초 접속·재접속을 1회씩 측정했다.

| 조건 | 변경 전 | 최종 변경 후 |
| --- | ---: | ---: |
| 첫 브라우저·첫 서버 조회 표본 | 3.354초 | 1.235초 |
| 서버 캐시 준비 후 새 브라우저 2회 | 0.313~0.383초 | 0.276~0.321초 |
| 같은 브라우저 재접속 3회 | 0.143~0.167초 | 0.095~0.218초 |
| 최초 클라이언트 목록 API 요청 수 | 2회 | 0회 |

첫 표본의 SDK 스크립트 응답은 변경 전 2.826초, 변경 후 0.152초였다. 외부 네트워크 편차가 크므로 첫 표본의 전체 차이를 코드 개선 효과나 보장되는 시간으로 해석하지 않는다. 변경 후 첫 표본에서는 SDK 요청이 접속 후 0.171초에 시작됐고, HTML 스트림의 DOMContentLoaded 시점은 1.039초였다. 기존에 대화에서 측정한 개발 서버의 2.28초와 이 프로덕션 수치를 직접 비교하지 않는다.

실제 휴게소 247개·주유소 226개를 같은 Node 프로세스에서 비교했을 때 시설 연결 계산 중앙값은 83.7ms에서 6.8ms로 줄었다(준비 실행 2회 후 각 10회). 전체 반환값이 변경 전과 같고 연결된 주유소 217개도 동일함을 확인했다. 이 값은 시설 연결 계산 시간이며 전체 화면 표시 시간과 구분한다.

측정 스크립트는 등록된 `localhost:3000` origin을 유지하면서 Chromium의 주소 매핑으로 측정용 프로덕션 서버에 연결한다. 실행 중인 개발 서버의 프로세스나 설정은 변경하지 않는다. 원본 결과와 화면 PNG는 Git에서 제외한 `.map-performance/`에 저장한다.

```powershell
# 프로덕션 서버를 실행한 터미널과 별도 터미널에서 측정한다.
node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3318
node scripts/measure-initial-markers.mjs current
```

### 검증

- 관련 단위 테스트 46개 통과: 시설 연결·필터, 노선 별칭과 거리 동률, 주유소 검색, 검색 캐시, 마커 갱신.
- SDK 모의 API 회귀 9개, 실제 DB 서버 초기 데이터·노선 전환 1개, 실패한 서버 초기 조회의 최신 API 재시도 1개 통과. 총 11개 브라우저 시나리오다.
- 변경 파일 ESLint, TypeScript 및 프로덕션 빌드 통과. 기존 Next.js 보안 업데이트 권고는 남아 있으며 의존성 버전은 변경하지 않았다.
- 서버 부트스트랩은 기본으로 활성화한다. API fixture를 사용하는 SDK 모의 회귀에서는 실행 스크립트가 테스트 서버에만 `E2E_CLIENT_MAP=1`을 적용한다. 실제 DB를 읽는 부트스트랩 검증은 파일을 명시해 별도로 실행한다.

```powershell
node scripts/run-playwright-e2e.mjs e2e/kakao-map-zoom.spec.ts --output=test-results/client-map
$env:E2E_READONLY_DB = '1'
node scripts/run-playwright-e2e.mjs e2e/mobile-bootstrap.spec.ts --output=test-results/bootstrap
```

오류 복구 시나리오는 `E2E_BOOTSTRAP_FAILURE=1`과 접속할 수 없는 로컬 테스트용 `DATABASE_URL`을 해당 테스트 프로세스에만 지정해 실행한다. 실제 DB를 수정하지 않는다. 브라우저 테스트를 동시에 실행할 때는 결과·보고서 디렉터리도 각각 분리해야 한다.
